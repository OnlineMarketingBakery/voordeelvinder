# 0001 — Astro 7 instead of Astro 5

- **Date:** 2026-09-29
- **Status:** Accepted (Tanjil delegated the choice; pushback raised in Phase 0)
- **Brief:** §0, §4.1 say Astro 5.

## Context

On 2026-09-29 the npm registry showed:

| Line | Newest release | Released   |
| ---- | -------------- | ---------- |
| 7.x  | 7.3.5          | 2026-09-24 |
| 6.x  | 6.4.8          | 2026-06-17 |
| 5.x  | 5.18.2         | 2026-05-26 |

Astro's policy is to give "extended maintenance for security fixes only for one previous
major version". In practice 6.x hasn't had a release since 7.0 shipped, and advisories whose
ranges include 5.x were fixed only in 7.x. Among them is a critical remote-code-execution bug
in image optimisation, GHSA-26w7-cxv4-gfx2, which affects `astro <7.2.8` and is fixed in
7.2.8 with `sharp >=0.35.4`.

This site runs a public Node server that handles personal data. Starting it on a major that
no longer gets security fixes, and then migrating (Zod 3→4, Vite 6→8, the Rust compiler,
build-time `import.meta.env` inlining), would cost more than starting on 7.

## Decision

Build on **Astro 7.3.x**, with `@astrojs/node` 11, `@astrojs/react` 7 and Zod 4 (`astro/zod`
re-exports Zod 4).

Nothing in the brief depends on Astro 5:

- content collections use `src/content.config.ts` with loaders;
- page transitions are native CSS view transitions, not `<ClientRouter />`.

## Consequences

- **TypeScript is pinned to ~6.0**, because `@astrojs/check` and `typescript-eslint` don't
  accept TS 7 yet.
- **Accessibility linting uses the `eslint-plugin-jsx-a11y-x` fork:** ESLint 10, which
  `eslint-plugin-astro` 3 requires, isn't supported by the original plugin.
- **`import.meta.env` values are inlined at build time**, including non-`PUBLIC_*` ones. So
  secrets are read only through `src/server/env.ts`, and lint enforces this (see 0004).
- **`compressHTML` now defaults to `'jsx'`**, which can drop spaces between inline elements
  across line breaks. Check rendered copy when building pages.
